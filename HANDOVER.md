# Cadence — handover

A single-file personal web app for pacing indulgences on a fixed cadence, with a
weight trend underneath. Built in a chat session; this doc exists so the next
session doesn't relitigate settled design decisions.

Current state: `index.html` works, standalone, no dependencies, no network.
Open it in a browser and it runs. It is also an installable PWA when served over
HTTPS — see "Installing" below.

---

## What it does

Three tiers of indulgence. Each refills on a timer and caps at a maximum you can
hold. Tap a tile when you have one. That's the whole interaction.

| Tier | Refill | Max held |
|---|---|---|
| Snack | 36h | 2 |
| Indulgent meal | 7 days | 1 |
| Big night | 30 days | 1 |

Below that: a daily weight input, a 60-day chart, and a free-text if-then plan.

---

## Design decisions — settled, don't reopen without reason

**It is a cooldown, not a currency.** The original idea was a token economy —
earn credit by exercising, spend it on food. That was deliberately cut. Nothing
is earned, there is no balance, and there is no way to argue your way into more.
The whole point is that the decision is made in advance, while calm, rather than
negotiated in the moment. Any feature that lets good behavior buy indulgences
reintroduces exactly the problem this design removes.

**Three tiers, not four.** Every tier boundary is a judgment call made while
hungry. Fewer boundaries, less drift.

**Round-up rule.** Anything between two tiers is charged as the bigger one.
Stated in the UI. This is the single most important line in the design — it
removes the judgment call and biases it against the user by default.

**Overage borrows forward.** Going over drops the balance negative and it
refills from there. Floor is -3. There is no penalty, no streak to break, no
"ruined week." All-or-nothing rules are the failure mode being designed against,
so the overage path has to be boring and survivable.

**No carryover.** The max-held cap is the mechanism. Unused allowance evaporates
rather than accumulating, because an accumulating balance is a currency again.

**7-day trailing average is the headline number.** Daily readings render as
faint dots behind it. Day-to-day weight noise is a couple of kg on water alone
and reacting to it is how people quit.

**Recalibrate monthly, not weekly.** The "Adjust cadence" panel edits refill
hours and caps. It's intended to be touched against the 30-day delta. Anything
faster turns the cadence into a negotiation.

**The if-then field is not decoration.** The buttons can't do anything about a
bad day. That field is where the substitute behavior gets written down in
advance.

## Technical notes

- The app is one file. Vanilla JS, no build step, no external requests, no
  fonts. The manifest, worker and icons sit beside it and the app does not
  depend on them.
- Persistence is `localStorage` under key `cadence.v1`, with an in-memory
  fallback if storage throws.
- Balances accrue continuously from a stored `lastAccrue` timestamp — not by
  daily tick — so the app is correct after being closed for a week.
- Re-renders every 60s and on `visibilitychange`.
- `FLOOR = -3` and the tier defaults are constants near the top of the script.

## Installing

Done. The page was renamed `cadence.html` → `index.html` so a static host serves
it at the site root, and the rest is the usual PWA trio:

- `manifest.json` — standalone display, `#131a21` on both theme and background,
  192/512 icons plus maskable variants. `start_url` and `scope` are `./` so the
  app works from a project subpath (`/health-tracker/`) as well as a root domain.
- `sw.js` — cache-first over the shell with a background revalidate, so a deploy
  lands on the second launch. Bump `VERSION` when the shell changes anyway.
- Registration in `index.html` is guarded on `https:`/`localhost`, because
  `file://` origins are `null` and registration throws there. Opening the file
  off disk still works exactly as before.
- `icons/` are generated by `tools/mkicons.py` — pure stdlib, no image
  libraries. Re-run it if the mark or palette changes; the PNGs are committed.

Verified in headless Chromium: worker reaches `active` and controls the page,
an offline reload still returns the app, and `file://` loads clean with no
console errors and no registration attempt.

### One-time setup on GitHub

`.github/workflows/pages.yml` deploys the repo root to Pages on every push to
`main`. It needs Pages switched on once, by hand:

**Settings → Pages → Build and deployment → Source: GitHub Actions.**

Until that is set the workflow run fails at `configure-pages`. After it, the app
is at `https://davidnurkkala.github.io/health-tracker/` and Chrome's install
prompt has everything it needs.

Everything lives in localStorage, so offline worked after first load regardless.
The service worker is there to satisfy installability more than to do real
caching work.
